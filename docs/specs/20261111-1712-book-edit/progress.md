### 새 테스트가 실패하는 것을 본 방법

- `chapterEdit`: 무작위 검사는 `mapRange`의 새 시작 위치에 1을 더하니 seed 1에서 실패했다. 예시 테스트는 구현을 쓰는 도중 실패하는 것을 봤다(공백까지 맞추던 첫 구현에서 메모가 무관한 낱말에 붙는 경우가 무작위 검사 seed 24로 드러났다).
- `backup` 4.7-2 첫 테스트: 옮긴 메모의 `updatedAt`을 올리지 않게 바꾸니 실패했다.
- `area.emu`, `rules`: 서브에이전트가 옛 구현으로 되돌려 실패를 봤다(4.3-10의 동시 읽기 반복 테스트는 옛 구현에서도 가끔 통과해, 순서를 정해 만든 두 테스트가 다시 읽기 경로를 맡는다. 4.7-6 규칙 테스트는 지금 규칙의 통과를 확인하는 것이라 실패를 볼 수 없다).
- `BookEditor`, `ChapterEditor`, `bookEdit`: 새 화면과 새 함수의 테스트라 기능이 없으면 가져오기부터 실패한다. 따로 되돌려 보지는 않았다. `ChapterEditor` 4.3-3은 처음에 글이 크게 줄 때의 확인 창 때문에 실패해, 확인 창이 실제로 뜨는 것을 봤다.
- `edit.emu` 4.6-3: 읽는 범위를 지키는지 보는 테스트라 기능 없이 실패하는 것을 보지 않았다.

## 재량 결정

- 새 장 id는 `c-` + `createId()`(시각+난수)로 만든다. 쓴 적 있는 id를 기억할 필요가 없고 책 정보에 항목을 더하지 않는다.
- 화면은 주소가 따로 있는 두 화면으로 둔다: 책 편집 `#/book/<id>/edit`, 장 본문 편집 `#/book/<id>/edit/<장 id>`. 뒤로 가기와 나가기 확인을 주소 변화 한 곳에서 다룬다.
- 본문 비교는 문단 단위로 먼저 맞추고, 바뀐 구간만 낱말 단위로 비교한다(`fast-diff` 1.3.0). 낱말만 맞추고 공백·문장 부호는 낱말 사이의 틈으로 본다. 공백까지 맞추면 통째로 다시 쓴 문장에서 무관한 낱말끼리 짝지어져 메모가 엉뚱한 글에 붙는다. 낱말 수가 같고 사이 글이 같으며 낱말끼리 닮았으면(절반 이상 같은 글자) 낱말 하나씩 바뀐 것으로 본다(오타 여러 개를 함께 고친 경우).
- 문단 단위 맞춤으로 붙이지 못한 메모는 본문 전체를 낱말 단위로 한 번 더 비교해 본다(문단을 옮기면서 그 사이 문단도 고친 경우).
- 위치를 옮긴 메모는 `updatedAt`을 저장 시각으로 올린다. 고친 뒤 받은 백업을 옛 상태에 가져올 때 파일 쪽 메모가 이기게 하기 위해서다(4.7-2). 그래서 본문을 고치면 그 메모들이 모아 보기에서 위로 올라온다.
- 제목은 입력을 마칠 때(포커스 이동, Enter) 바로 저장하고, 순서·추가·삭제도 누르는 즉시 저장한다. "저장" 버튼을 따로 두지 않았다.
- 책 편집 화면은 이 책이나 메모가 다른 곳에서 바뀌면 다시 읽고 알린다. 저장할 때도 책의 고친 시각을 다시 확인한다.
- 동시 수정은 저장할 때 저장소의 본문을 다시 읽어 편집을 시작할 때의 본문과 비교해 알아챈다. 저장소의 본문이 이미 저장하려는 글과 같으면 저장된 것으로 본다(저장이 끝났는데 화면이 실패로 안 경우).
- 글자 수 상한(200만 자)은 글이 늘어나는 저장만 막는다. 이미 상한을 넘은 책도 줄이거나 같은 길이로 고칠 수 있다(명세서 4.3-8은 "넘으면 저장하지 않는다"인데, 성능 시드의 큰 책이 상한을 조금 넘어 있어 오타도 못 고치는 것을 보고 정했다).
- 편집 입력칸은 값을 React 상태로 두지 않는 기본 `textarea`다. 20만 자에서 글자마다 다시 그리지 않게 하고, 변경 요약과 찾은 개수는 입력이 0.2초 멈춘 뒤 계산한다.
- Firestore 본문 조각의 문서 id를 `장~판~번호`로 바꿨다. 목록 문서(`chsizes`)의 항목이 지금 판을 가리키고, 그 항목을 책 정보·메모와 같은 묶음으로 바꾼다. 지울 조각은 항목의 `p`에 적어 다음 쓰기가 지운다. 조각을 지우는 마지막 단계가 실패해도 저장은 성공으로 본다. 예전 배치(`장~번호`)의 장은 그대로 읽고, 다시 쓸 때 새 배치로 옮긴다.
- 지운 장에 남긴 메모의 출처는 모아 보기의 기존 표시(책 제목만)를 그대로 쓴다.
- 찾기: 버튼으로 찾으면 본문에 포커스를 두고, 찾을 글 입력칸에서 Enter로 찾으면 포커스를 입력칸에 돌려준다.

## 놓친 점

- [명세서] 4.4-1은 "고른 글이 바뀌지 않았으면 유지"라고만 했는데, 문단을 다른 자리로 옮기면서 그 사이의 문단도 고치면 옮긴 문단과 엇갈린 문단의 메모를 붙일 자리를 하나로 정할 수 없는 경우가 있다. 4.4-4(확실하지 않으면 붙이지 않는다)를 따라 "유지 못함"으로 알리게 했고, 무작위 검사도 문단을 옮긴 경우에는 "엉뚱한 자리에 붙지 않는다"만 본다.
- [명세서] 4.3-8의 글자 수 상한이 이미 상한을 넘은 책(성능 시드, 또는 상한이 생기기 전의 책)을 어떻게 다룰지 정하지 않았다. 글이 늘어나는 저장만 막는 쪽으로 정했다.
- [명세서] 저장 계층을 고치니 "이 버전보다 옛 빌드는 이 버전이 저장한 장을 읽지 못한다"는 호환 문제가 생겼다. 명세서는 "기존에 저장된 장은 그대로 읽혀야 한다"만 요구해 새 빌드가 옛 데이터를 읽는 쪽만 지켰다. 여러 PC를 쓰면 모두 다시 빌드해야 한다는 것을 문서와 보고서에 적었다.
- [명세서] 4.3-14의 "0.3초 넘게 걸리는 동작에는 대기 표시"는 실제 저장이 0.1초라 화면에서 볼 수 없었다. 0.3초 뒤에 표시가 나오게 만들었고, 대기 상태 스크린샷은 찍지 못했다.
- [프로세스] 성능 측정을 `| tail`로 걸러 돌려 멈춘 단계를 두 번 놓쳤다. 측정 스크립트에 단계 로그(표준 오류)를 넣었다.
- [프로세스] 서브에이전트가 파일을 고치는 동안 내 커밋을 검증하려고 `git stash --keep-index -u`를 썼다. 그 사이 서브에이전트의 파일이 잠깐 사라졌다(충돌 없이 되돌아왔다). 같은 작업 공간을 나눠 쓸 때는 쓰지 말아야 한다.
- [프로세스] 개발 서버(`npm start`)가 떠 있는 동안 다른 파일을 고치면 페이지가 새로 고쳐져 성능 측정이 중간에 끊긴다.
- [프로세스] 내장 브라우저 창이 숨겨져 있으면 `requestAnimationFrame`이 돌지 않아 화면 확인 스크립트가 끝나지 않는다. 화면 확인은 `shoot.mjs`와 Playwright로 했다.
